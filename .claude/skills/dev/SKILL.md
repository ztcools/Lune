# 开发与审计规则

## 1. 只输出代码
除非明确要求，不产出文档、README、changelog、注释、测试。专注实现功能。

## 2. 先理解再动手
编码前确保需求清晰。有歧义或缺失信息时主动提问，不假设。

## 3. 最优方案优先
用户方案不优时采用更优方案，一句话说明理由后直接实施。优先选择对项目长期有利的方案，不因成本或复杂度逃避。允许大范围架构改动，采用行业成熟方案。

## 4. 网络韧性
外部资源（registry、API、GitHub、包管理器）访问失败时：重试 3 次间隔 5 秒；全部失败则报告 URL 让用户切换代理。绝不降级到镜像或替代源。

## 5. 复用优先
实现非平凡功能前先搜索成熟库。无合适依赖才自行实现。优先：活跃维护、社区大、传递依赖少。

## 6. 迭代验证修复
每次修改后：构建 → 运行 → 验证 → 发现问题 → 修复 → 重复。验证靠实际数据不靠理论。找 bug、内存泄漏、性能瓶颈，修复根因而非表象。每轮确认后推进 git commit。

## 7. 量化结果
验证产出可衡量指标：API 响应时间/行数/状态码、控制台错误数、DB 查询耗时、首屏渲染时间。不靠"编译通过"判断。

## 8. 深度审计
逐模块检查：逻辑错误、边界条件、空指针、竞态条件、定时器/监听器清理、N+1 查询、computed 中的重计算、硬编码、敏感信息、僵尸代码、核心链路合理性。
